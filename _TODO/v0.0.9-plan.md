# gofake v0.0.9 実装計画

**目的**　`Faker` の生成器へのアクセスを整理し、5 ロケールを追加する。ensoria の `seed --locale` から新ロケールを利用できるようにし、README の英語版と日本語版を独立させる。

**対象**　`gofake`、`encli`、`ensoria-template` は別々の Git リポジトリ。公開モジュールの更新順序は gofake → encli → ensoria-template とする。gofake の作業ブランチは `release/v0.0.9`。今回のリリースで Go の最低要件を `1.24.2` から `1.26.4` に引き上げる。

## 1. `Faker` の公開 API とコア生成器の直アクセス

`pkg/faker/faker.go` の `newFaker` は、共通の `*core.Rand` を受け取り、すべての生成器を初期化する。現在の `Faker` は `Rand` と各生成器を公開するため、`f.Rand` の再代入で `f.Rand.Num` と初期化済みの `f.Person` が別々の乱数源を参照する状態を作れる。

**決定**　コア 6 種を含む全 19 カテゴリをメソッドに統一し、`f.Num().IntBt(1, 10)`、`f.Barcode().EAN13()` のように呼び出す。`Faker` は非公開の `rand *core.Rand` と各生成器の参照を管理する。これにより、カテゴリを取得する構文がそろい、呼び出し元は `Faker` の生成器フィールドを再代入できない。アクセサ名は `Get` を付けない Go の慣例に従う。[Effective Go — Getters](https://go.dev/doc/effective_go#Getters)

`Num() *core.RandNum` は初期化済みの生成器を返すだけなので、取得を繰り返しても乱数列は進まない。同じカテゴリを続けて使う場合は `num := f.Num()` として `num.IntBt(...)` を呼べる。Go でメソッドを括弧なしで参照した `f.Num` の型は `func() *core.RandNum` になるため、アクセサ方式で `f.Num.IntBt(...)` という構文は使えない。アクセサが保護するのは `Faker` が持つ参照であり、返したポインタの参照先は Go の型システム上、書き換えられる。[Go 言語仕様 — Method values](https://go.dev/ref/spec#Method_values)

| `*Faker` のメソッド | 戻り値 |
| --- | --- |
| `Bool()`、`Num()`、`Str()`、`Time()`、`Slice()`、`Map()` | 順に `*core.RandBool`、`*core.RandNum`、`*core.RandStr`、`*core.RandTime`、`*core.RandSlice`、`*core.RandMap` |
| `Person()`、`Color()`、`Address()`、`Barcode()`、`Company()`、`File()`、`Image()`、`Internet()`、`Lorem()`、`Medical()`、`Payment()`、`PhoneNumber()`、`UserAgent()` | 各ジェネレーターパッケージの既存ポインタ型。例 `Barcode() *barcode.Barcode` |

- [ ] `gofake/pkg/faker/faker_test.go` で、4 つの既存コンストラクタから全 19 アクセサが利用でき、同じ `Faker` から繰り返し取得した生成器が同一ポインタを返すことを確認する。`fk_suite_test.go` を再利用する。
- [ ] `gofake/pkg/faker/seed_test.go` で、シード `42` の未使用の `Faker` に対する `Num()`、`Str()`、`Person()` の混在呼び出しが、同じシードを渡した `core.NewRand` と同じ `person.New` を共有乱数源で呼んだ場合と一致することを確認する。取得だけを先に繰り返しても乱数列が進まないことを含める。時刻の比較には固定の `TimeRange` を使い、`Map` の動作確認には 1 要素のマップを使う。
- [ ] `gofake/pkg/faker/faker.go` でアクセサを実装する。コアの 6 メソッドは `f.rand` の既存ポインタをそのまま返す。カテゴリ以外の用途の乱数 API は引き続き `core.NewRand` から利用できる。`Faker.Rand` は公開 API から外し、互換エイリアスの追加は省く。`core.Rand` のフィールドと各生成器の `New` は現行のままとし、生成器内の `r.Num` などには現行の `core.Rand` API を使う。
- [ ] `gofake/examples/main.go` と gofake 内の旧 API 呼び出しを移行する。下流では `ensoria-template/internal/module/{user,post}/db/seeder/seeder.go`、`internal/plamo/apidoc/example.go`、`encli/pkg/seeder/seeder.go` のサンプルが該当する。`Seed(faker.Faker)` 自体は既存のインターフェースと合わせる。Go のアドレス取得可能な引数や変数からポインタレシーバーを呼び出せる。
- [ ] `gofake` で `go test ./pkg/faker/...` と `go run ./examples` を実行する。

## 2. 追加ロケールとデータの検証

**決定**　v0.0.9 では、下表の 5 ロケールを追加する。Go 公式の 2025 Developer Survey の居住国設問（回答 3,453 件）を参考に、既存対応の米国に続くグラフ上の 5 か国を選んだ。割合は丸められた調査回答の構成比であり、回答者は北米・欧州に偏っている。[Go 公式調査](https://go.dev/blog/survey2025)・[居住国グラフ](https://go.dev/blog/survey2025/location.svg)

| 優先順 | ロケール | 居住国の回答割合 | レビューするローカル表記 |
| --- | --- | --- | --- |
| 1 | `de_DE` | ドイツ 11% | ウムラウトを含む人名、通り名と番地の順序、5 桁郵便番号 |
| 2 | `en_GB` | 英国 5% | 国内電話番号、外向き・内向きコードから成る大文字の郵便番号 |
| 3 | `fr_FR` | フランス 5% | アクセントを含む人名と地名、番地と通り名の順序、5 桁郵便番号 |
| 4 | `en_CA` | カナダ 4% | 州・準州の略号、英大文字と数字を交互に並べる `A1A 1A1` 形式 |
| 5 | `en_IN` | インド 4% | ラテン文字のインド人名、州・都市表記、6 桁の PIN コード |

カナダでは英語版を初回対象とし `fr_CA` は次の候補にする。インドはまず `en_IN` とし、`hi_IN` など各言語固有の文字体系を持つロケールは個別に扱う。言語と地域の組み合わせは、既存の `ja_JP` と同じ `language_REGION` 形式で統一する。[カナダ政府の言語案内](https://www.canada.ca/en/immigration-refugees-citizenship/services/settle-canada/language-skills.html)・[インド政府の言語案内](https://rajbhasha.gov.in/en/bharat-samhita-code-of-india-)

- [ ] `gofake/pkg/faker/provider/locale/<locale>/` ごとに `constructor.go`、`people.go`、`addresses.go`、`companies.go`、`phonenumbers.go` を作る。既存ロケールの構造に沿って、`New() *provider.Localized` から `People`、`Addresses`、`Companies`、`PhoneNumbers` を初期化する。テンプレートを設定した項目には対応する `Create...` コールバックも設定し、ふりがなや米国の EIN など地域固有の項目は対象地域のデータがある場合のみ提供する。
- [ ] データのレビューでは、個別の実在レコードを集めず、合成可能な名前・地名・組織形態と公開された書式を使う。FakerPHP からデータを移植する箇所は、由来のバージョン・ファイルと既存 `LICENSE` の帰属表示を確認する。郵便・電話は書式に沿ったテストデータを提供し、住所の実在性・配達可能性を API の仕様に含めない。電話は公開されているフィクション用番号帯を優先する。[UPU の国別住所資料](https://www.upu.int/en/postal-solutions/programmes-services/addressing-solutions)・[Canada Post](https://www.canadapost-postescanada.ca/cpc/en/support/articles/addressing-guidelines/postal-codes.page)・[India Post](https://www.indiapost.gov.in/locate-postoffice)・[Ofcom](https://www.ofcom.org.uk/phones-and-broadband/phone-numbers/numbers-for-drama)・[Bundesnetzagentur](https://bundesnetzagentur.de/DE/Fachthemen/Telekommunikation/Nummerierung/DramaNumbers/artikel.html)
- [ ] `en_GB` と `en_CA` の郵便番号は、書式に合う大文字を固定した複数のマスクと数字プレースホルダーを使う。既存の `AlphaDigitsLike` の `?` は小文字も生成するため、直接使わない。新ロケールで国内電話番号を確認する際は `PhoneNumber().PhoneNumber()` を使う。`E164PhoneNumber()` の実装はグローバルデータを参照する。
- [ ] 各パッケージの `constructor_test.go` と 1 個の `locale_suite_test.go` に Ginkgo の検証を置く。`CreateWithLocaleAndSeed(locale.New(), 42)` を 2 つ作り、`Person().Name()`、`Address().City()`、`Address().StreetAddress()`、`Address().Address()`、`Address().Postcode()`、`Company().Name()`、`Company().JobTitle()`、`PhoneNumber().PhoneNumber()` が、同じ呼び出し順で再現可能かつ非空であることを確認する。書式はロケールごとの期待値を用意し、複数の固定シードで郵便番号、国内電話番号、アクセント付き文字を含むテンプレートの出力を検証する。既存の仕様と実装の食い違いが見つかった場合は、期待するケースに `FIXME: consider fixing the implementation.` を付けてスキップし、修正の判断を仰ぐ。
- [ ] `gofake` で `go test ./pkg/faker/provider/locale/...` と `go test ./pkg/faker/...` を実行し、既定ロケールが `en_US` であることと `ja_JP` の生成テストが通ることを確認する。

## 3. encli の検証と seed ランナーの接続

`encli/cmd/seed.go` は `validation.Locale` で入力を検証している。現在のランナーは `ja_JP` を特別扱いし、残りを `faker.Create()` に流す。許可リストだけ更新すると新ロケールが `en_US` で実行される。また、ランナーの `go run` は利用側プロジェクトを起点とするため、モジュールの選択は encli バイナリのビルド時とは別に確認する。

- [ ] `gofake/CONTRIBUTING.md` の英語・日本語の節に、ロケール追加時は encli の `seed --locale` も更新する手順を追記する。`cmd/seed.go`、`internal/common/validation/validation.go`、`internal/seed/generator/generator.go` を示し、受け入れテストと利用プロジェクトの gofake 依存更新も確認項目にする。別リポジトリへの参照には [encli ソース](https://github.com/ensoria/encli) を使う。
- [ ] `encli/internal/common/validation/validation.go` の `supportedLocales` に 5 コードを加え、既存 2 コードと空文字 → `en_US` の動作を保つ。`encli/cmd/seed.go` の `--locale` ヘルプを更新する。対応コードをヘルプでも一覧表示する場合は同じ許可リストから組み立てる。
- [ ] `encli/internal/seed/generator/generator.go` の `generator.Params` に `Locale string` を足し、`seed.go` から検証済みの値を渡す。`Generate` も同じ `validation.Locale` を通し、`en_US` は `faker.Create()`、その他は選択された 1 パッケージだけを `localeData` として import して `faker.CreateWithLocale(localeData.New())` を使うソースを生成する。`createFaker()` の戻り値は既存の `RunAll` に合わせて `faker.Faker`。ロケールを生成時に確定させ、`runner.Run` と生成された `main` の内部引数は `env` と `appPath` のみにそろえる。
- [ ] 生成時に対象を決めることで、新しい encli バイナリから従来の `en_US`・`ja_JP` を選んだときは、生成ソースが新ロケールの Go パッケージに依存しない。新ロケールの利用手順には、利用側モジュールで `github.com/ensoria/gofake` を `v0.0.9` 以上に更新することを明記する。利用側の `github.com/ensoria/encli` モジュールを新しい版に上げる場合も、間接依存で gofake が上がり得るので、旧 Faker API の移行を同じ手順で案内する。[Go の最小バージョン選択](https://go.dev/ref/mod#minimal-version-selection)
- [ ] 既存の `validation_test.go` と `generator_test.go` にケースを追加する。7 コードと空文字を受け入れ、`xx_XX` を拒否すること、生成ソースが対象ロケールの import とコンストラクタを使い、既定のランナーに新ロケールの import が含まれないことを確認する。`go test ./internal/common/validation ./internal/seed/... ./pkg/seeder ./cmd` を encli で実行する。

## 5. ブランチ運用とリリース順序

| 運用 | 利点 | 注意点 |
| --- | --- | --- |
| **短命なリリースブランチ（今回の推奨）** | gofake の API・ロケール・README を 1 つのリリース候補に集め、encli とテンプレートとの組み合わせを確認してから `main` に統合できる。 | `main` 側に並行変更が入った場合は同期して再検証する。現在の gofake CI は `main` / `develop` 向け PR を対象とするため、作業 PR をリリースブランチへ出す場合はローカル検証を行い、必要に応じて CI の PR 対象を追加する。 |
| GitHub flow | 変更単位で短命ブランチから `main` へ PR を出し、レビューと CI を早い段階で通せる。公開版はリリースタグで特定できる。 | リリースの区切りはタグとマイルストーンで管理する。作業途中に公開タグを切る場合は、対象コミットに必要な変更がすべて入っているかを確認する。 |
| 継続的なリリースブランチ | Kubernetes の `release-X.Y` のように、安定系列の修正と次期開発を同時に進められる。 | 修正のバックポートと保守期間を管理する運用が必要。旧系列の保守が必要になった段階で選ぶ。 |

[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)・[Kubernetes のリリースサイクル](https://kubernetes.io/releases/release/)
